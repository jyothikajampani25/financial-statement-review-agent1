1. Purpose of this document

The BRD says what the service must do. This design says how it is structured and how it looks.

Build starts only after this design is reviewed against BR-01 to BR-11.

2. Design rules (from the BRD)

RuleDesign meaning
Numbers are checked by rulesMath, consistency, and YoY engines produce pass/fail and amounts. GenAI does not invent totals.
Show evidenceEvery finding and observation carries line name, year, amount, and check id.
Explain, do not inventObservation text is written only from rule results + statement lines already retrieved.
Clear review packUI shows summary, findings, variances, and observations in one place.

3. High-level architecture

MVC + Service layers. Names are roles, not product brands.

Figure 1 — system architecture

View → Controller → Services → Model. Validation and YoY own numbers. Observation svc explains rule output only.

3.1 What each block does

BlockResponsibility
View (UI)Upload / select company years, run review, show pack. Never invent amounts on screen.
ControllerAccepts review request, calls services in order, returns one review pack DTO.
Validation serviceMath totals + Balance Sheet identity (+ other simple consistency rules).
YoY serviceCompares current vs prior; flags material absolute / % change.
Observation serviceTurns findings + variances into short review comments with evidence attached.
Model / storeNormalized statement lines, review runs, findings, observations.

3.2 Architecture alternatives (why this one)

OptionVerdict
A. Pure LLM reads the spreadsheet and “reviews”Rejected — numbers can be hallucinated; weak evidence.
B. Rules only, no GenAI commentsPossible but weaker UX for “review observations”.
C. Rules for truth + GenAI for wording (chosen)Selected — matches BR-05/BR-06; auditable; demo-ready.

4.2 Review pipeline (Level 1)

A. Load statements

CSV / JSON / sample rows → map to standard lines → store current + prior year.

If mapping is wrong here, later checks are noisy. Keep a small line dictionary.

B. Run review (every request)

Validate math → consistency → YoY → build findings → write observations from findings → return pack.

Figure 3 — DFD Level 1 (review pipeline)

Findings are machine results. Observations are human-readable text grounded on those findings.

9. Think big — platform capabilities (still simple)

Core review stays the same. These blocks make the agent enterprise-ready and score on integration, performance, monitoring, and reuse.

9.1 Integration alternatives (plug into any environment)

ChannelHow it connectsWhen to use
REST APIPOST /reviews, GET /reviews/{id}, GET /healthAny backend, ERP adapter, RPA bot
Webhook outPush review-complete / critical-fail JSON to a URLTicketing, Slack/Teams bots, workflow tools
UI embedSame API behind Streamlit / portal iframeFinance team day-to-day
File dropWatch folder / S3 → enqueue reviewBatch month-end packs
Chat surfaceTeams/Slack command calls the same Controller“Review Acme 2023” from chat

One Controller contract. Many fronts. That is the reusable design.

9.2 Pipeline + traffic (optimization)

Figure 6 — sync demo path vs async scale path

Demo runs sync. Scale path: enqueue → parallel workers (math ∥ YoY) → observations → notify. Cache mapped lines by company+year.

LeverDesign
PipeliningValidation and YoY are independent → run in parallel workers; Observation waits for both.
TrafficAPI rate limit + job queue; return 202 Accepted + run id under load.
CacheNormalized line map cached; invalidate on re-upload.
IdempotencySame company+years+hash → reuse pack (no double GenAI spend).

9.3 Notifications, health, auto-mail

EventWho gets itChannel
Review completedRequesting reviewerIn-app + email / webhook
Critical finding (MATH/CONS fail)Reviewer + optional finance leadEmail subject: company · check id · run id
Service unhealthyOps / on-callHealth probe fails → auto email (and optional Slack)
Job stuck / timeoutOpsAlert with trace id

Health contract: GET /health checks API process, DB/store reachability, and (optional) GenAI key configured. Down → alert. No silent failure.

9.4 Trace + feedback loop

Trace (every run)

  • trace / run id on every log line
  • who started, when, company, years
  • counts: pass / fail / material
  • duration of each service step

Feedback (every observation)

  • Reviewer marks useful / not useful
  • Stored against observation + check id
  • Feeds prompt / template tuning
  • Shown in demo as continuous improvement
